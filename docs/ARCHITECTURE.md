# Go Daily — Architecture

This document describes how Go Daily is built and the conventions that keep it consistent. Update it whenever a structural decision changes.

## 1. System overview

```text
            ┌────────────────────┐        ┌─────────────────────┐
 Browser ──▶│  admin-web (Next)  │──────▶ │                     │
 (Arabic    │  BFF: server comps │ Bearer │   api (FastAPI)     │──▶ PostgreSQL 16
  RTL UI)   │  + server actions  │ token  │   services/models   │    (system of record)
            └────────────────────┘        │                     │
 Android  ─────────────────────────────▶  │                     │
 driver app        HTTPS + Bearer token   └─────────────────────┘
```

- **PostgreSQL** is the single system of record. All schema changes go through Alembic migrations.
- **api** owns all business rules and authorization. Clients are untrusted.
- **admin-web** is a backend-for-frontend (BFF). The browser never sees the API token, which lives in an `httpOnly` cookie. Server Components and Server Actions call the API from the Next.js server.
- **driver-android** (from Task 09) talks to the API directly with a bearer token stored in Android Keystore-backed storage.

## 2. Monorepo layout

```text
apps/api/
  app/
    core/        config, db, logging, errors, security, time helpers
    models/      SQLAlchemy ORM models (one module per domain area)
    schemas/     Pydantic request/response models
    services/    business logic (use cases); the only place that writes data
    api/         FastAPI routers (thin), dependencies (auth, RBAC)
    cli.py       operational commands (seed, bootstrap-admin, detect-exceptions, prune-*)
  alembic/       migrations (hand-reviewed)
  tests/         pytest suite against real PostgreSQL
apps/admin-web/
  src/app/       App Router routes
  src/components UI components (presentational; no business rules)
  src/lib/       API client, session helpers, formatting
packages/config  tsconfig base and design tokens (theme.css and tokens.ts)
packages/shared  shared TS constants (roles, Arabic labels)
```

## 3. Backend conventions

### Layering

| Layer | Responsibility | Must not |
| --- | --- | --- |
| Route handler (`app/api/routes`) | Parse input, resolve current user, call a service, shape the response | contain business rules or queries beyond trivial lookups |
| Service (`app/services`) | Validate business rules, write data, write audit records, commit | depend on FastAPI request objects |
| Model (`app/models`) | Table structure and constraints | contain workflow logic |
| Schema (`app/schemas`) | Input validation (types, lengths, formats) and output shape | expose sensitive fields (password hashes, national IDs unless authorized) |

Services raise domain errors (`app/core/errors.py`): `NotFoundError`, `ConflictError`, `ValidationFailed`, `PermissionDenied` and so on. A global handler maps them to one envelope:

```json
{ "error": { "code": "conflict", "message": "رسالة بالعربية", "details": {} } }
```

`code` is stable and machine-readable. `message` is Arabic for direct display.

### Database

- **UUID primary keys**, generated in Python (`uuid4`) with `gen_random_uuid()` as the server default.
- **Timestamps** use `timestamptz`. Store UTC and show Africa/Cairo. Business-day boundaries ("today's shifts") are computed in the configured local timezone (`app/core/time.py`).
- **Money** uses `NUMERIC(14,2)` and **quantities** use `NUMERIC(14,3)`. Python uses `Decimal` and JSON carries strings. Binary floating point is never used for money.
- **Constraint naming convention** is defined in `app/models/base.py`, so migrations stay deterministic.
- **History is preserved.** Corrections create new records or audited updates. Historical facts are not hard-deleted (see Audit below).
- Migrations are autogenerated and then **reviewed by hand**. Never edit a migration that has already been applied in a shared environment.

### Transactions

A request gets one SQLAlchemy session (`get_db`). Services commit explicitly at the end of a use case. A use case that fails rolls back as a whole. Tests wrap each test in an outer transaction with savepoints, so service commits never leak between tests.

### Time

All server code uses `app.core.time.utcnow()`. Do not call `datetime.now()` without a timezone.

## 4. Frontend conventions

- **Arabic-first RTL.** `<html lang="ar" dir="rtl">`. Use logical Tailwind utilities (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`) instead of left/right. Numbers, plates and codes use the `ltr-nums` helper so they read left-to-right.
- **Latin digits** in numbers and money (`ar-EG-u-nu-latn`), matching receipts and inputs.
- **Design tokens** live in `packages/config/tokens/theme.css` (Tailwind v4 `@theme`) and are mirrored in `tokens.ts` for charts and maps:
  - dark forest green for primary and navigation
  - bright lime for actions, active state and GPS indicators
  - white surfaces on a light neutral background
  - charcoal text

  No purple/blue SaaS palette, glassmorphism or decorative animation.
- Business rules stay in the API. UI components only present data and collect input.
- Next.js 16 conventions:
  - `proxy.ts` replaces `middleware.ts`.
  - Request APIs are async.
  - `cacheComponents` is intentionally **off**: every admin screen is authenticated and dynamic.

## 5. Security model

### Authentication (Task 02)

- **Credentials:** phone number plus password. Phone numbers are normalised to the Egyptian mobile format `01XXXXXXXXX`; `+20`, `0020` and Arabic-Indic digits are accepted.
- **Password storage:** Argon2id (`argon2-cffi`). Hashes are upgraded automatically at login when parameters change. Policy: 8–128 characters, not containing the phone number, not trivially repetitive.
- **Sessions:** opaque random tokens (`gd_` plus 256 bits), not JWTs.
  - Only the SHA-256 of the token is stored (`auth_sessions.token_hash`).
  - The table is checked on every request, so logout, deactivation, role change and password reset take effect immediately.
  - Absolute lifetime: `SESSION_TTL_HOURS_ADMIN` (default 12h) for web, `SESSION_TTL_HOURS_DRIVER` (default 30d) for the driver app.
  - Web sessions also expire after `SESSION_IDLE_TIMEOUT_HOURS` of inactivity.
  - `last_used_at` is written at most every 5 minutes.
- **Client separation:** the admin web (`client: "web"`) accepts staff roles only. The driver app (`client: "mobile"`) accepts `DRIVER` accounts only.
- **Brute force:** after `LOGIN_MAX_FAILED_ATTEMPTS` wrong passwords the account is locked for `LOGIN_LOCKOUT_MINUTES` and the API returns 429 `account_locked`. Unknown phones and wrong passwords return the same error and take similar time (the hash is verified against a dummy value).
- **Inactive accounts:** login is rejected (`account_inactive`), and existing sessions are rejected on the next request.
- **Admin web (BFF):** the token is kept in an `httpOnly`, `SameSite=Lax` cookie (`gd_session`), marked `Secure` when `SESSION_COOKIE_SECURE=true`. All API calls happen server-side (Server Components and Server Actions). `proxy.ts` only does an optimistic redirect when the cookie is missing. A 401 from the API sends the user to `/auth/clear`, which deletes the cookie. Server Actions have Next.js's built-in origin checks against CSRF.
- **Bootstrap:** the first `SUPER_ADMIN` is created by `python -m app.cli bootstrap-admin` from `BOOTSTRAP_ADMIN_*` environment variables. The command refuses to run if one already exists. There are no default accounts or passwords.

### Authorization (RBAC)

Roles: `SUPER_ADMIN`, `ADMIN`, `OPERATIONS`, `ACCOUNTANT`, `DRIVER`.

- Permissions are fine-grained strings (`vehicles:write`, `settlements:finalize`, …) defined in `app/core/permissions.py`. Roles map to permission sets there, and endpoints declare what they need with `require_permissions(...)`.
- `OPERATIONS` runs the fleet: vehicles, drivers, assignments, shifts, routes, tracking, maintenance and operational exceptions. It has no financial write access.
- `ACCOUNTANT` handles the financial ledgers, settlements and profitability. Fleet data is read-only.
- `DRIVER` has **no** staff permissions. Drivers use dedicated `/api/v1/driver/*` endpoints that are always scoped to their own records.
- National IDs need `drivers:read_sensitive`, which only admins hold.
- User management rules:
  - `ADMIN` manages `OPERATIONS`, `ACCOUNTANT` and `DRIVER` accounts. Only `SUPER_ADMIN` manages admin accounts.
  - Users cannot change their own role or deactivate themselves.
  - The last active `SUPER_ADMIN` cannot be demoted or deactivated.
- The admin web hides navigation by permission for convenience only. The API is the enforcement point.

### Audit trail

- `audit_logs` is append-only. A PostgreSQL trigger rejects `UPDATE`, `DELETE` and `TRUNCATE`, and actor foreign keys do not cascade.
- An audit row is written in the same transaction as the change it describes. It records actor, action, entity, a field-level diff, reason, IP, user agent and request ID.
- Passwords, password hashes, tokens and national IDs are never written. For those fields only `{"changed": true}` is recorded.
- Recorded authentication events: login success and failure (unknown phones are masked), lockout, logout, password change and reset, activation and deactivation, role changes.

### Other controls

- Authorization is enforced in the API on every endpoint. The frontend only hides navigation for convenience.
- Credentials and tokens are never logged. The JSON log formatter also redacts known sensitive keys.
- CORS allows only configured origins. Interactive API docs are disabled in production.
- Security headers on the admin web: `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`.

## 6. Domain model (operations core)

```text
VehicleType 1─* Vehicle *─┐                       ┌─* Driver ─? User(DRIVER)
                          ├─ DriverVehicleAssignment (history, PRIMARY/RELIEF)
                          │
OperationType(kind) 1─* RouteDefinition 1─* RouteStop (ordered, lat/lng/radius)
                          │
Shift (driver, vehicle, PLANNED→ACTIVE→COMPLETED|CANCELLED, odometer start/end)
  1─* OperationSession (operation type, optional route; one ACTIVE per shift)
Driver 1─* DriverCompensationPlan (versioned by effective dates)
```

- **No permanent bindings.** A vehicle has no `driver_id` or operation type. Who drives is in the assignment history, and what it does is in the shifts and sessions.
- **Operation behaviour** is keyed on `OperationType.kind`, never on a specific route, school or place. Admins can add types (for example a factory shuttle) that reuse a kind.
- **Shift invariants:**
  - The database allows one ACTIVE shift per driver and per vehicle (partial unique indexes).
  - The driver must be assigned to the vehicle at start. Staff may override with a reason; the driver app never can.
  - An expired driver or vehicle license blocks the start.
  - Odometer readings never go below the vehicle's last reading, and end ≥ start.
  - The distance per shift is capped at 1,500 km.
  - Corrections are audited with old and new values and a reason.
  - Staff may backdate up to 7 days. The driver app always uses server time.
- **Odometer and GPS distance** are kept separate. Shifts report `odometer_distance_km` only; GPS distance comes from the tracking phase. They are compared by the reconciliation in [`GPS_INTEGRITY.md`](GPS_INTEGRITY.md#gps-vs-odometer-reconciliation-u04). The first-entered readings are kept when corrected.

### Route events and loop detection (Task 12, U09)

`app/services/geofence.py` turns a session's valid GPS points into events, deterministically (same points, same events). `app/services/route_events.py` stores them.

- **Geofences.** Each stop is a circle (lat/lng/radius). Points less accurate than `ROUTE_MAX_ACCURACY_M` (50 m), or than the fence's own radius, are ignored for that fence.
- **Debounce.** An entry or exit counts only after `ROUTE_MIN_POINTS` (2) consecutive points over at least `ROUTE_DWELL_SECONDS` (20 s). It is timestamped at the first point of the run.
- **Legs.** A leg runs from leaving one terminal (origin or destination) to entering the other. It counts only if it took at least `ROUTE_MIN_LEG_MINUTES` (3), because close or overlapping terminals can make GPS noise look like a trip. Faster legs are stored as `LEG_REJECTED` with the measured time and are not counted.
- **Incomplete legs.** A leg that comes back to its own terminal after at least the minimum time, or is still open when the session ends, is stored as `LEG_INCOMPLETE` with the reason. While a session is running, an open leg is simply in progress.
- **Evidence.** Every leg event carries `details`: start time, duration, from and to terminal, the intermediate stops visited, and whether they were visited in route order.
- **Loops (round-trip routes).** A loop is two consecutive completed legs in opposite directions (موقف → جامعة → موقف). Legs and loops are both kept and numbered.
- **Duplicates.** Each event has a dedupe key (session, type, stop, second). Recomputing updates sequence numbers and evidence, and voids automatic events that are no longer produced (reason `superseded_by_recompute`). Events voided by staff stay voided.
- **Manual correction.** Staff can add a reached/leg/loop event or void any event, always with a reason, and each step is audited.
- **Counts.** Sessions report `loops`, `legs` and `incomplete_legs`; the route-loops report has the same columns.

Tests: `test_geofence_engine.py` (debounce, accuracy, loops, minimum leg time, incomplete legs, evidence, determinism), `test_route_events_api.py` (from uploaded GPS to stored events and counts, recompute, manual correction).

### School route verification (Task 13, U12)

A school run is one scheduled duty (route, date, scheduled start and end, vehicle, driver). It links to the operation session that starts within an hour of its window. When the session ends, `school_runs.evaluate` decides the outcome from GPS and stores what it rests on in `school_runs.verification`.

- **Required stops:** every stop of the route that has coordinates.
- **Reached stops:** stops with an active entry event in the session (GPS or audited manual event).
- **Delays:** start delay (actual start − scheduled start) and arrival delay (first arrival at the destination − scheduled end).
- **Also stored:** GPS coverage of the session and the largest distance from the straight lines between stops. Deviation is shown for context only; the `ROUTE_DEVIATION` rule handles it.

| Outcome | When |
| --- | --- |
| مكتملة | Every required stop reached, start and arrival within `SCHOOL_LATE_GRACE_MINUTES` (10) |
| مكتملة بتأخير | Every required stop reached, but the start or the arrival was later than the grace period |
| غير مكتملة | Some stops not reached although GPS covered at least `SCHOOL_MIN_GPS_COVERAGE_PCT` (60 %) of the session |
| تحتاج مراجعة | Stops not reached and GPS too thin to tell; no verdict is guessed |
| فائتة | The window passed with no session (unchanged) |

- **Re-evaluation.** A run is re-evaluated when late GPS arrives, unless staff set its status. Status corrections need a reason, are audited, and are never overwritten by later GPS.
- **Not yet:** a per-stop "optional" flag, for example when a pupil is absent. Until then staff correct the outcome with a reason. Per-stop settings belong to route versioning (U08).

Tests: `test_school_verification.py` (each outcome, evidence, corrections kept), `test_route_events_api.py` (linking, missed runs, late sync).


## 7. Financial model (Tasks 14-19)

```text
FuelType(category FUEL|CONSUMABLE) 1─* FuelTransaction ─┐
ExpenseCategory(pnl_group)          1─* Expense         ├─ vehicle, driver?, shift?
RevenueEntry (kind) 1─* RevenueReceipt (cash|electronic, held by DRIVER|COMPANY)
RideHailingPlatform 1─* RideHailingStatement ──approve──▶ RevenueEntry (SYSTEM)
Driver 1─* DriverLedgerEntry (signed; balance = company owes driver)
Driver 1─* DriverSettlement (DRAFT → FINALIZED → VOIDED, frozen details)
```

- **One lifecycle for financial records.** Fuel, expenses, revenue and statements are SUBMITTED, then APPROVED or REJECTED. A rejected record can be edited and resubmitted. Approved records are never edited: a correction voids the original and creates a replacement linked by `corrects_id`, both kept and audited. Nothing financial is deleted. Totals count APPROVED records only, and pending records are reported as such.
- **Money** is `Numeric(14,2)` end to end, crosses the API as decimal strings, and is quantised with ROUND_HALF_UP for display.
- **No double counting.** `RevenueEntry` is the only revenue source for reports. Ride-hailing revenue can only be generated from an approved platform statement (at most one live entry per statement, enforced by a partial unique index). Platform commission is recorded as `fees_withheld` on that entry. Money received is a receipt, never a second revenue row.
- **Driver custody.** Receipts held by the driver post a `CASH_COLLECTED` debit to the driver account. A cash handover is a credit. Costs paid by the driver become a `REIMBURSEMENT` credit once approved. Voiding the source voids its ledger entry; a source posts at most one live entry (partial unique index).
- **Settlements** compute compensation from the versioned plans in force, freeze the calculation (plan terms, inputs, lines) when finalised, and post a single `EARNING` entry. Finalised settlements of one driver cannot overlap (exclusion constraint). A plan change never touches a finalised settlement; redoing one means voiding it with a reason.
- **Vehicle P&L** uses approved records only. Amounts with a service period (contracts, statements, settlement earnings) are spread over it by days. Driver earnings are split across vehicles by driving minutes, and costs across operation types by session minutes. Missing inputs produce warnings, never estimates.
- **Platforms are not scraped or integrated.** Statements are entered manually from what the platform provides.

### Fuel efficiency (U13)

`app/services/fuel_efficiency.py` groups data per vehicle by shift, day, week (Saturday start) or month. The report is *كفاءة الوقود* (`fuel_efficiency`, with a period filter).

- **Distance** is the odometer distance of completed shifts.
- **Fuel** is approved purchases of fuel-category types (CNG, gasoline, diesel). Engine oil and other consumables are never part of efficiency.
- **Figures:**
  - gasoline and diesel: km per litre, L/100 km and EGP/km;
  - CNG: km per unit in the unit it was recorded in (m³ or kg; the default unit is set on the fuel type), and EGP/km.
  - Quantities of different units are never added together.
- **Bi-fuel vehicles.** When a period has more than one fuel, the distance is shared and cannot be split. Per-fuel km/unit is marked approximate. The combined EGP/km (all fuel cost ÷ distance) is the comparable figure, and it is also given per vehicle for the whole range.
- **Purchases are not consumption.** A refuel covers the driving that follows, so shift figures are indicative and weeks or months are steadier. Purchases not tied to a shift are counted, and shown in a note, in the per-shift view.
- **Missing data.** A missing odometer reading or zero distance gives no figure, never an estimate. Ratios round half-up.

Tests: `test_fuel_efficiency.py`.

### Vehicle fuel baselines (U14)

`app/services/fuel_baselines.py` judges each complete week (Saturday to Friday) of each vehicle.

- **Metric.** A week with one fuel is compared on physical efficiency (km per litre, m³ or kg), so a fuel price rise never looks like higher use. A week with several fuels (CNG + gasoline) cannot split its distance, so it is compared on cost per km. Unit prices are shown with it.
- **Baselines.**
  - Historical: the median of the vehicle's previous `FUEL_BASELINE_WEEKS` (12) usable weeks with the same metric and fuel.
  - Recent: the median of its last `FUEL_RECENT_WEEKS` (4) such weeks, shown for context.
  - Peer: other vehicles whose main operation type (by session minutes) was the same over those weeks. It is used when the vehicle's own history is too short.
- **Minimum sample.** At least `FUEL_BASELINE_MIN_WEEKS` (4) of the vehicle's own weeks, or `FUEL_PEER_MIN_SAMPLES` (6) peer vehicle-weeks. Otherwise the result is "بيانات غير كافية".
- **Incomplete data.** Weeks with a missing odometer reading or less than `EXCEPTION_FUEL_MIN_WEEK_KM` (150) are neither used as a baseline nor judged. They are counted as excluded weeks.
- **Verdict.** A week worse than its baseline by `EXCEPTION_FUEL_RATIO` (1.6×) or more is **استهلاك غير معتاد — مراجعة مطلوبة**. The `FUEL_CONSUMPTION` review rule raises it with every baseline, sample size and threshold as evidence. Only approved fuel records count.
- **Where:** the rule, and the report *خط الأساس لاستهلاك الوقود* (`fuel_baselines`), which shows every vehicle-week with its baselines and the reason when no verdict was possible.

Tests: `test_fuel_baselines.py`, `test_exceptions.py` (unusual use flagged; a price-only rise not flagged).

### Refuelling plausibility (U15)

`app/services/fuel_plausibility.py` checks one purchase at a time. The fuel record page shows the checks as *فحوص المعقولية*, from `GET /api/v1/fuel/{id}/plausibility`. Each check passes, fails, or is "لا يمكن الفحص" when the data it needs is missing; nothing is assumed.

| Check | Fails when | Threshold settings |
| --- | --- | --- |
| Assignment | The recorded driver was neither assigned to the vehicle nor driving it in a shift | — |
| Shift time | No shift of the vehicle around the purchase. Context only (depot refuels are normal); driver-paid cases are raised by `FUEL_OUTSIDE_SHIFT` | `EXCEPTION_FUEL_OUTSIDE_SHIFT_MINUTES` |
| Odometer | The reading is below the previous fuel record's, or outside the covering shift's readings | `FUEL_ODOMETER_TOLERANCE_KM` (5) |
| Location | The purchase position is far from the vehicle's GPS at that time. Raised by `FUEL_FAR` | `EXCEPTION_FUEL_DISTANCE_M` |
| Quantity | Above the per-purchase maximum for its unit, or more than `FUEL_QUANTITY_RATIO` (2×) the vehicle's median purchase of that fuel once it has `FUEL_QUANTITY_MIN_HISTORY` (5) purchases | `FUEL_MAX_QUANTITY_LITER` (100), `_CUBIC_METER` (40), `_KG` (30) |
| Rapid repeat | Another purchase of the same fuel within `FUEL_REPEAT_HOURS` (6) and either less than `FUEL_REPEAT_MIN_MINUTES` (60) apart or less than `FUEL_REPEAT_MIN_KM` (50) driven in between | as listed |
| Duplicate | Same vehicle, fuel and amount close in time. Raised by `DUPLICATE_TRANSACTION`. A pair that is both a duplicate and a rapid repeat gives one case | `EXCEPTION_DUPLICATE_WINDOW_MINUTES` |

The review rule `FUEL_PLAUSIBILITY` ("مراجعة مطلوبة") raises one case per purchase for failed assignment, odometer, quantity or rapid-repeat checks, with every check as evidence. Failures that have their own rule are not raised twice. There is no tank-capacity field yet, so the absolute quantity limits are fleet-wide settings.

Tests: `test_fuel_plausibility.py`.

### Expected collection per loop (U10)

`app/services/expected_revenue.py` compares what a fixed route should have collected with what was recorded.

- **Rates** (`route_revenue_rates`) are set per route by finance staff (`revenue:write`; operations cannot) on the route page. There are three models:
  - an amount per completed loop (round-trip routes only);
  - an amount per completed leg;
  - planned passengers per leg × fare. The passenger figure is a planning assumption typed in by staff. It is never inferred from GPS.
- **Versioned by date.** A new rate closes the previous one the day before. Past days keep the rate that applied then, and both steps are audited.
- **Expected** = completed loops or legs detected on that day's sessions (GPS plus audited manual corrections; incomplete and rejected legs never count) × the rate in force that day.
- **Recorded** = "تحصيل خط ثابت" revenue entries for the same vehicle and day. Approved and pending amounts are shown separately, and the difference uses both, so an entry waiting for approval does not look like a shortfall.
- **Results per vehicle and day:**
  - مطابق للمتوقع: within the allowance;
  - **فرق تحصيل — مراجعة مطلوبة**: short by more than the allowance;
  - أعلى من المتوقع;
  - لا يوجد سعر متوقع: a fixed route without a rate, so no expected figure is invented;
  - تحصيل بدون دورات مسجلة;
  - اليوم لم ينتهِ بعد: a shortfall on the current day.
- **Allowance:** the larger of `COLLECTION_TOLERANCE_AMOUNT` (50 EGP) and `COLLECTION_TOLERANCE_PCT` (10 %) of the expected amount.
- **Where:** the report *التحصيل المتوقع من الدورات* (`expected_collection`, `revenue:read`), and the review rule `COLLECTION_GAP` for finished days. The rule is labelled "مراجعة مطلوبة" and its summary starts with "فرق تحصيل — مراجعة مطلوبة". A shortfall can have ordinary causes (collection not yet recorded, a wrong loop count), so the wording never suggests theft.

Tests: `test_expected_revenue.py`.

### Driver daily workflow: day-off, start photo, close-out, cash collection

From the design «تطبيق السائق» and «تحصيل نقدية السائقين». Code: `app/services/day_offs.py`, `app/services/cash.py` (writes), `app/services/cash_views.py` (board and account), routes `driver_cash.py` and `cash.py`, migration 0017.

- **Day-off («تسجيل اليوم إجازة»).** `DriverDayOff` (one live row per driver and day; cancelling keeps the row). Refused while a shift is running or after one started that day; while it stands, no shift can start for that driver on that day (driver app or office), so no location is collected. Drivers register today only (`POST /driver/day-off`, `/day-off/cancel`); the office can plan or cancel any day (`/day-offs`).
- **Odometer start photo.** The app uploads the photo first (`POST /driver/odometer-photo`, owner `driver`, kind `ODOMETER_PHOTO`) and sends its id with `POST /driver/shifts/start`. The start claims it: it must be this driver's, unused and at most `DRIVER_START_PHOTO_MAX_AGE_MINUTES` (120) old; it then moves to the shift (`shifts.start_odometer_photo_id`). Required from the app while `DRIVER_START_PHOTO_REQUIRED` is true (default); office starts from paper do not need it.
- **Close-out («تقفيل الوردية»).** `POST /driver/shifts/{id}/closeout` ends the shift if it is still running and records, in one transaction: the collection as a revenue entry with a receipt held by the driver (ride-hailing excepted: platform statements stay its only revenue source, so the cash is tracked but not booked), gas and gasoline as driver-paid fuel (`CNG`, `GASOLINE`), «الكارتة» as a `TOLL` expense, and maintenance or oil change as a `REPAIR` or `OIL_CHANGE` expense whose note is required. Every record is `SUBMITTED` from `DRIVER_APP` and goes through the usual office review. The old per-purchase fuel entry from the app stays available.
- **Net to hand over.** Collection less the expense lines that are submitted or approved. Corrections are followed to the live record, and a rejected or voided line stops being deducted, so the driver owes it. Nothing is estimated.
- **Cash collection.** A manager records what was actually received (`POST /cash/collections`, `cash:collect`), against a close-out or as an older remainder. It cannot exceed what the driver owes; it posts a `CASH_HANDOVER` credit to the driver ledger, so after review the ledger nets to zero for a fully handed-over day. Collections and close-outs are voided with a reason, never edited; a close-out with live collections cannot be voided, and voiding one voids the records it created. The office can then re-enter it (`POST /cash/shifts/{id}/closeout`) for the ended shift with the same end reading.
- **Carry-over.** Close-outs are walked in order per driver: each shows what was carried from before, the total due, what was collected on it and what remains, which carries to the next. The driver sees the same in «حسابي مع الإدارة» (`GET /driver/account`); staff see it per driver (`/drivers/{id}/cash-account`) and per day on the board (`/cash/board`: close-outs, shifts still running or ended without a close-out, and day-offs).
- **Permissions.** `cash:read` (operations, accountants, admins) and `cash:collect` (accountants, admins).
- **Admin web.** `/cash` («تحصيل نقدية السائقين», full-screen workspace): day summary, one card per close-out with every line (rejected lines struck through and marked as due from the driver), the start photo and fuel receipts, status and carry-over, the collect dialog (defaults to what is still due) and voiding a collection with a reason; day-offs and open or unclosed shifts are listed with them.

Tests: `test_driver_cash.py`; existing driver-app tests now send a start photo.

### Attachments (Task 24)

- `Attachment` rows hold metadata only (owner type and id, kind, original name, sniffed content type, size, sha256, storage key, uploader, soft-delete reason). Owners: fuel transactions, expenses, revenue entries, platform statements, maintenance records, vehicles, shifts (odometer start photo), close-outs (fuel receipt) and drivers (a start photo not yet used).
- Bytes live behind `app/core/storage.py`: a local directory (default) or any S3-compatible bucket, selected by `STORAGE_BACKEND`. No vendor is required. Keys are generated by the server, never derived from file names. Buckets are assumed private.
- The content type comes from the file's magic bytes, not the browser; only JPEG, PNG, WebP and PDF are accepted, up to `ATTACHMENT_MAX_BYTES`.
- Files are served only through `GET /attachments/{id}/content` after the same permission check as the owning record, with `nosniff` and a sandbox CSP. The admin web proxies them through `/files/[id]` with the session cookie.
- Files are never hard-deleted. Removing one needs a reason and is audited. Evidence on approved or voided records is locked. A file identical to one already stored (same sha256) is accepted with a "review needed" warning, since a reused receipt is worth a look but not proof of anything.

### Maintenance (Task 21)

```text
MaintenanceType (default interval_km / interval_days) 1─* MaintenanceSchedule (per vehicle: overrides, baseline)
Vehicle 1─* MaintenanceRecord (review lifecycle, parts/labour/other, downtime) ─?→ FuelTransaction (oil purchase)
```

- The next due point is computed from the latest approved record of that type, or from the schedule's baseline when the system has no record yet. Without either, the state is "no baseline" rather than a guess.
- Due soon = within max(500 km, 10% of the interval) or 14 days; overdue = past either limit.
- An oil purchase stays a consumable fuel transaction. A service record may link to it, but its cost is not added again; the record carries its own parts, labour and other cost.
- Maintenance cost in the vehicle P&L = approved maintenance records + approved expenses in maintenance-group categories. Staff are told not to record the same invoice in both places.

### Exception detection (Task 20)

```text
RULES (app/services/exception_rules.py) ──▶ Candidate(rule, severity, summary, evidence, links, dedupe_key)
        │ run_detection (CLI hourly / "run now" in the web), one run at a time (advisory lock)
        ▼
OperationalException (OPEN → UNDER_REVIEW / ESCALATED → EXPLAINED / CORRECTED / DISMISSED; reopen with a note)
ExceptionRun (window, per-rule counts, per-rule errors)
```

- **Signals, not verdicts.** Every case carries one of two neutral labels, "مراجعة مطلوبة" or "حالة غير معتادة", plus the facts and thresholds the rule used. The UI says so on every case page. No rule infers intent.
- **Rules:** GPS switched off or permission withdrawn during a shift; GPS gaps (with how far the vehicle moved); mock location; GPS integrity (U02: tracking stopped or restarted with the time lost and likely reboots, impossible jumps, late uploads, points sent from outside the shift, phone clock offset and batches going back in time; see [`GPS_INTEGRITY.md`](GPS_INTEGRITY.md)); long stops away from the route's own stops; route deviation (corridor around straight lines between stops, not road geometry); outside the configured operating areas (disabled until `EXCEPTION_OPERATING_AREAS` is set); odometer increase between shifts (no tracking outside shifts, so this comes from readings); implausible or backwards odometer; GPS vs odometer distance (only with ≥ 80% GPS coverage); fuel cost per km against the vehicle's own weekly history; fuel recorded far from the vehicle (only when both locations exist); driver-paid fuel outside any shift; the same file on different records; same amount/type/vehicle records close in time; platform statements with no recorded ride-hailing activity or far-off income per hour.
- **Thresholds** are environment settings (`EXCEPTION_*`), returned with the rule list by `GET /api/v1/exceptions/rules`.
- **Dedupe.** Each case has a stable key (per shift, session, record or week). A later run updates an active case's evidence; a closed case is never reopened or rewritten. If a later run re-checks a case's scope and no longer finds it (e.g. a duplicate was voided), the case is marked "no longer detected" but stays for the reviewer.
- **Failure isolation.** Each rule runs in a savepoint; a failing rule is logged and recorded on the run, and the others still run.
- **Audit.** Every review step is an audit entry with the status change, the note and the resolution.

### Notifications (Task 22)

- One `Notification` row per recipient, generated from the current state by `python -m app.cli generate-notifications` (hourly) or the admin "refresh now" button: vehicle licence/insurance and driver licence expiry, maintenance overdue or due soon, tracking interrupted during an active shift (after a grace period), open exception cases of medium or high importance, and a daily summary of financial records waiting for review.
- Recipients are active staff users whose role holds the generator's permission (drivers never receive admin notifications).
- **No spam:** `(user, dedupe_key)` is unique; keys change only when the situation does (expiring → expired, a new tracking interruption after recovery). Low-importance cases stay on the exceptions page, and pending reviews come as at most one summary per day.
- **Self-clearing:** a run that no longer produces a condition marks its notifications cleared (hidden from the inbox, kept in history). The bell counts unread, uncleared rows; critical ones turn it red.
- **Channels:** in-app is always on. Push, e-mail, WhatsApp or SMS plug in through the `NotificationChannel` interface (`deliver(notification, user)`), enabled by name in `NOTIFICATION_CHANNELS` with a minimum severity. They run after commit, only for new rows, and a failing provider is logged without affecting others. Only a development `log` channel ships; no vendor is hardwired.

### Reports (Task 23)

- Every report is a `ReportDef` in `app/services/reports.py`: the permissions its data needs, the filters it accepts, and a builder returning columns, rows, summaries and notes. One shape serves the web table, JSON and CSV.
- Totals are computed from the rows returned, never from a separate query, so each total is traceable to its records. Financial reports use approved records only, and say so in the notes.
- Access: `reports:read` **and** every permission of the underlying data (e.g. revenue needs `revenue:read`). The catalog hides what a user cannot open, and the API refuses it anyway.
- Limits: one year per request and 20,000 rows; beyond that the user is asked to narrow the filters (no silent truncation).
- CSV: UTF-8 with BOM (Excel shows Arabic correctly), money as plain decimals, local times, a totals row, and text cells starting with `= + - @` prefixed with `'` to block spreadsheet formula injection. The web downloads through `/reports/[code]/csv`, which forwards the session.
- PDF is not offered: reliable Arabic shaping and right-to-left layout in generated PDFs was not verified, and the spec allows CSV only in that case.

### Data integrity and concurrency (Task 26)

Services validate and return clear errors. Row locks serialise competing writes to the same record. Database constraints are the final guard, so a bug or a race can never store a broken state.

| Concern | Service behaviour | Database guarantee | Tests |
| --- | --- | --- | --- |
| Active driver/vehicle assignments | Locks the driver and vehicle rows, then checks for overlap | `btree_gist` exclusion constraints (no overlapping primary assignment per vehicle/driver) | `test_assignments.py::test_database_rejects_overlap_even_without_the_service` |
| Shift lifecycle | Locks the shift; start/end/cancel only from the right state | Partial unique indexes: one active shift per driver and per vehicle, one active session per shift. Check constraints: active needs start time and reading, completed needs end time and reading | `test_shifts.py::test_one_active_shift_per_driver_and_vehicle`, `test_integrity.py` |
| Odometer monotonicity | Start reading ≥ vehicle's last reading; end ≥ start; implausible jumps refused; corrections need a reason | `end_odometer_km >= start_odometer_km`, non-negative readings | `test_shifts.py`, `test_integrity.py` |
| Duplicate GPS batches/points/events | Batch replay answers from the stored result | Unique (driver, client batch id), (shift, client point id), (driver, client event id) | `test_tracking.py` |
| Duplicate financial submissions | Driver-app writes take an `Idempotency-Key`. Admin forms disable submit while pending; near-identical records are also flagged by the exception engine | Unique (user, idempotency key); one live revenue entry per statement; one live ledger entry per source | `test_finance_costs.py`, `test_integrity.py` |
| Review actions (approve, reject, void, correct) | `finance_common.fetch(lock=True)` takes `SELECT … FOR UPDATE` on every write path; the second reviewer sees the first decision and gets 409 | Lifecycle columns and the unique indexes above | `test_integrity.py::test_review_actions_lock_the_record` |
| Settlement finalisation | Locks the settlement; finalising freezes the calculation (plan terms, inputs, lines) | Exclusion constraint: finalised settlements of one driver never overlap; one live `EARNING` entry per settlement | `test_finance_settlements.py` |
| Loop detection duplication | Recomputing voids its own previous automatic events | Unique `dedupe_key` per route event; one school run per session | `test_route_events_api.py`, `test_integrity.py` |
| Exception and notification runs | One detection run at a time (advisory lock); upserts by key | Unique `dedupe_key`; unique (user, dedupe key) | `test_exceptions.py`, `test_notifications.py` |
| Audit records | Written in the same transaction as the change they describe (commit both or neither) | Triggers block `UPDATE`, `DELETE` and `TRUNCATE` on `audit_logs` | `test_auth.py`, `test_integrity.py` |

Admin web create forms do not send idempotency keys: the browser cannot resubmit while a request is pending, and the Next.js server does not retry API calls. Mobile writes need keys because they are retried on bad networks.

## 8. Observability

- JSON logs (one object per line) with a request ID. The ID is taken from `X-Request-ID` or generated, and echoed in the response.
- Liveness is `GET /health`. Readiness is `GET /ready`, which runs `SELECT 1` against the database and returns 503 on failure.

## 9. Local infrastructure

`compose.yaml` runs `postgres`, a one-shot `migrate` job, `api` and `admin-web`. Production images run as non-root users and include health checks. Dockerfiles accept an optional BuildKit secret `extra_ca` for building behind TLS-intercepting proxies. The secret is never stored in an image layer.
